VERDICT: CASE A — COSMETIC EXPORT-LABELING MISMATCH. NO DB MISATTRIBUTION.

The opponent DB uses ONE uniform mapping everywhere:
    scraper raw key 'seatN'  ->  internal int N-1   (seat1->0 ... seat6->5)
applied at exactly two raw->internal conversion points, both identical:
  * src/nlhe/integration/scraper_schema.py: _seat_to_idx() / _SEAT_RE
    ("seat([1-6])" -> int-1) and _seat_dict_to_array(); module doc states
    "seat1 -> idx 0, seat6 -> idx 5"; hero default alias 'seat1' -> 0.
  * src/nlhe/opponent_db/parser.py: _seat_arr() (idx = int(k[4:]) - 1) for
    FrameView stacks/bets/folded/empty; _raw_dealer() round-trips the
    top-level 0-indexed dealer_seat int back to f"seat{ds+1}" for old logs.
Every DB seat field is internal 0-indexed: hands.hero_seat / dealer_seat /
sb_seat / bb_seat, hands.dealt_seats_json, hands.start_stacks_json keys,
hands.net_chips_json keys, actions.seat, showdowns.seat. No table or field
uses a different convention (cross-field consumers — extract script's
net_chips_json[str(seat)] lookups against dealt_seats — agree, see evidence).

The v1 candidates export (tools/scraper_folded_showdown_task/
stale_folded_candidates.jsonl) simply emitted the INTERNAL 0-indexed seat
without converting back to the scraper's 'seatN' labels and without
documenting the convention. Hence candidate seat i == scraper seat i+1.
The "drops hero and 1-indexes 5 opponents" reading is incorrect: the script
excludes hero/sb/bb seats from CANDIDACY (line `if seat in (hero_seat,
sb_seat, bb_seat): continue`) but never re-numbers anything; hero is internal
0 (raw seat1, fixed: all 20 sessions have hands.hero_seat == 0), so surviving
opponent ids happen to lie in 1..5, which mimics 1-indexing by coincidence.
